# 美团 AI Infra 面经

## 一面（技术面）

### 1. vLLM 的 PagedAttention 原理？
- KV Cache 按 block 分配，类似 OS 虚拟内存
- 逻辑地址 → 物理 block 的映射表（block_table）
- 消除碎片，显存利用率从 ~60% → ~95%
- **追问：block size 怎么选？**
  - 太小：block_table 大，间接寻址开销
  - 太大：内部碎片（最后一块未填满）
  - vLLM 默认 16 token/block，经验最优
- **追问：copy-on-write 怎么实现？**
  - beam search 多分支共享前缀 KV 时，先共享物理 block
  - 写入时才分配新 block，复制数据后修改 block_table

### 2. Tensor Parallel 列切 vs 行切的区别？
- **列切**（ColumnParallel）：W 按输出维切，Y = [XW1, XW2]，各卡独立算，无通信
- **行切**（RowParallel）：W 按输入维切，Y = X1W1 + X2W2，需 all-reduce
- Megatron 的 QKV 用列切，FFN up 用列切，FFN down 用行切
- **关键：ColumnParallel → GeLU → RowParallel 全程只一次 all-reduce**
- **追问：Embedding 怎么切？**
  - 按 vocab 维切，各卡只持有部分 vocab 的 embedding
  - 前向时 token 路由到持有该 vocab 段的卡，最后 all-reduce

### 3. 混合精度训练中 loss scale 的作用？
- FP16 梯度可能下溢（< 2^-24）
- loss scale：前向乘 S，反向梯度也乘 S，更新前除 S
- 动态 loss scale：溢出时减半，连续 N 步不溢出时翻倍
- **追问：bf16 为什么不需要 loss scaling？**
  - bf16 指数位与 fp32 相同（8位），动态范围足够
  - 但尾数只有 7 位（vs fp16 的 10 位），精度更低
  - 所以 bf16 不溢出但精度差，fp16 精度好但可能溢出

### 4. 手撕：实现一个简单的 KV Cache
```python
class KVCache:
    def __init__(self, n_layers, n_heads, d_head, max_len, dtype=torch.float16):
        self.cache = [torch.zeros(max_len, n_heads, d_head, dtype=dtype) for _ in range(n_layers * 2)]
        self.pos = 0
    def append(self, k, v):
        for layer in range(len(k)):
            self.cache[layer * 2][self.pos] = k[layer]
            self.cache[layer * 2 + 1][self.pos] = v[layer]
        self.pos += 1
    def get(self, layer):
        return self.cache[layer * 2][:self.pos], self.cache[layer * 2 + 1][:self.pos]
```

### 5. Continuous Batching vs Static Batching？
- **Static**：等 batch 中所有请求完成才能加入新请求，短请求被长请求拖累
- **Continuous**：每步 decode 后检查，完成的移出，新请求填入空位
- **token 级别**：配合 PagedAttention，batch 在运行中动态变化
- **追问：prefill 和 decode 怎么混排？**
  - prefill 计算密集（大矩阵乘），decode 访存密集（小矩阵乘 + 大 KV 读取）
  - vLLM 默认优先 prefill，但会限制 prefill 频率避免饿死 decode
  - Sarathi-Serve 提出 chunked prefill 与 decode 混排

### 6. Speculative Decoding 的接受率受什么影响？
- **draft model 质量**：与 target 越接近接受率越高
- **K 的选择**：K 太大后面 token 偏离严重，接受率下降
- **任务类型**：重复性高的任务（代码）接受率高，创造性任务低
- **加速比**：接受率 r 时，平均每步生成 r+1 个 token，加速约 (r+1)/2

## 二面（系统设计面）

### 7. 设计一个支持多 LoRA 适配器的推理服务
- **共享 base model**：base model 常驻显存
- **LoRA 热加载**：A/B 矩阵小，按需 swap
- **Batch 调度**：不同请求可用不同 LoRA，需在 batch 内区分
- **vLLM LoRA**：支持多 LoRA 并发，通过 `lora_name` 路由
- **显存计算**：base(7B fp16=14GB) + n × LoRA(rank=8, ~20MB) ≈ 14GB + n×20MB
- **追问：batch 内不同 LoRA 怎么高效计算？**
  - 方案1：按 LoRA 分组，每组单独算 ΔW×x
  - 方案2：batch 化配，用 scatter/gather 路由到对应 A/B
  - 方案3：CUDA kernel 内部根据 lora_id 查表

### 8. 推理服务 QPS 优化思路
1. Continuous batching（动态拼 batch）
2. Prefix caching（共享 system prompt 的 KV Cache）
3. Speculative decoding（draft model 加速）
4. 量化（W8A8 / W4A16 降显存提吞吐）
5. Tensor Parallel（大模型拆多卡）
6. **Chunked prefill**（长 prompt 分块，不阻塞短请求）
7. **Disaggregated serving**（prefill/decode 分离到不同 GPU 池）
8. **CUDA Graph**（固定形状的 decode 用图捕获消除 kernel launch 开销）

### 9. 设计一个模型推理监控告警系统
- **指标采集**：
  - QPS / latency P50/P95/P99 / TTFT (Time To First Token)
  - GPU 利用率 / 显存占用 / KV Cache 命中率
  - 队列长度 / 排队时间
- **告警规则**：
  - P99 > 阈值 → 延迟告警
  - GPU 利用率 < 50% → 资源浪费
  - OOM / 碎片化 > 阈值 → 显存告警
- **自动扩缩容**：根据 QPS 和队列长度自动调整 GPU 副本数
