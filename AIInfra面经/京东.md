# 京东 AI Infra 面经

## 一面（技术面）

### 1. ZeRO 三个阶段的显存节省？
| 阶段 | 切分内容 | 显存（每卡） | 通信 |
|------|----------|-------------|------|
| ZeRO-1 | Optimizer State | 4C + 2ψ | reduce_scatter |
| ZeRO-2 | + Gradient | 2C + 2ψ | reduce_scatter |
| ZeRO-3 | + Parameter | 4C + 2ψ/N | all_gather + reduce_scatter |

- C = 模型参数量，ψ = 梯度大小，N = GPU 数
- **追问：ZeRO-3 前向时参数不全怎么办？**
  - 每层前向前 all-gather 拼出完整参数，算完释放
  - 可加 pre-fetch 提前一层 all-gather 隐藏通信
- **追问：ZeRO++ 有什么改进？**
  - hpZ：节点内 DDP + 节点间 FSDP，减少跨节点通信
  - qgZ：梯度 INT4 量化后再 reduce-scatter，通信量降 4x

### 2. Pipeline Parallel 的 1F1B 调度？
- 相比 GPipe（所有前向后所有反向），1F1B 交错执行
- 优势：激活值显存从 O(N_stage × micro_batch) 降到 O(N_stage)
- Interleaved 1F1B：每个 stage 持有多个 chunk，bubble 降为 (PP-1)/(V×M+PP-1)
- **追问：warm-up 阶段做什么？**
  - rank r 先做 PP-r-1 个前向，填满 pipeline
  - 之后进入稳态：一前一后交替
  - 最后做剩余的反向

### 3. FlashAttention 为什么快？
1. **IO-aware**：分块计算，SRAM 中完成 softmax，减少 HBM 读写
2. **Online softmax**：无需实例化完整 N×N attention matrix
3. **Kernel fusion**：QK^T → softmax → AV 融合为一个 kernel
4. **反向也快**：重算前向（存 logits 而非 attention matrix）
- **追问：online softmax 的 m/l 校正公式？**
  - m_new = max(m_old, m_block)
  - l = l × exp(m_old - m_new) + sum(exp(S - m_new))
  - O = O × exp(m_old - m_new) + exp(S - m_new) @ V
- **追问：IO 复杂度从 O(N²d) 降到多少？**
  - O(N²d²/M)，M = SRAM 大小，当 d < M 时显著降低

### 4. 手撕：实现 Gradient Accumulation
```python
def train_step(model, batch, accum_steps, optimizer):
    loss = model(batch) / accum_steps  # 关键：除以 accum_steps
    loss.backward()
    if (step + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```
- **关键细节**：
  1. loss 必须除以 accum_steps，否则累积的是"和"非"均值"
  2. zero_grad 只在真实 step 后做
  3. 与 DDP 组合时，梯度同步只在真实 step 的 micro-batch 触发
  4. 与 AMP 组合时，unscale 只在真实 step 做

### 5. MoE 的负载均衡怎么做？
- **问题**：token 路由不均 → 部分 expert 过载，部分空闲
- **Auxiliary Loss**：L_aux = α × E × Σ(f_i × P_i)
  - f_i = expert i 被选中的 token 比例
  - P_i = expert i 的平均路由概率
  - 鼓励均匀路由
- **Token Dropping**：超 capacity 的 token 丢弃或传给次优 expert
- **DeepSeek aux-loss-free**：直接在路由权重加偏置，无需 aux loss
- **追问：capacity factor 怎么设？**
  - 一般 1.0-1.5，太小丢 token 多，太大浪费算力
  - 训练初期可以动态调整

### 6. GQA（Grouped Query Attention）的优势？
- **MQA**（Multi-Query）：所有 Q head 共享 1 对 KV，显存最省但质量下降
- **GQA**：Q head 分组，每组共享 1 对 KV，折中
- **显存**：KV Cache 从 n_heads × d 降到 n_kv_heads × d
- **推理加速**：KV 读取量减少，decode 更快
- Llama 3 用 GQA（32 Q heads, 8 KV heads）

## 二面（系统设计面）

### 7. 设计一个 MoE 训练系统
- **Expert Parallel**：每 GPU 持有部分专家，All-to-All 通信
- **负载均衡**：auxiliary loss 防止专家不均
- **Top-K Router**：每 token 选 2 个专家
- **Capacity Factor**：每专家最大处理 token 数，超限丢弃
- **通信优化**：All-to-All overlap 计算，grouped GEMM
- **追问：All-to-All 通信怎么 overlap？**
  - dispatch 阶段：本地 token 按 expert 归类后发给目标卡
  - 收到一部分 token 就开始计算，不等全部收完
  - combine 阶段：算完一部分就发回，overlap 后续计算
- **追问：DeepSeek MoE 的共享专家机制？**
  - 除 routed experts 外，有 1 个 shared expert 处理所有 token
  - 减少路由方差，降低 auxiliary loss 需求

### 8. 大模型训练 OOM 排查思路
1. `torch.cuda.memory_summary()` 看分配详情
2. 检查激活值大小（用 activation checkpointing）
3. 检查梯度累积是否正确
4. 检查 ZeRO 阶段是否够高
5. 检查混合精度是否开启
6. 检查 optimizer state（8bit optimizer）
7. **检查 batch size / seq_len 是否过大**
8. **检查数据加载是否 pin_memory 占用过多**
9. **用 `torch.cuda.memory._record_memory_history` 追踪泄漏**

### 9. 设计一个分布式推理框架的调度器
- **请求队列**：waiting（新请求）+ running（正在生成）
- **调度策略**：
  - 每 step 从 waiting 填入 running 空位
  - 预算限制：KV block 总数不超限
  - 优先级：短请求优先（减少尾延迟）
- **preempt 机制**：显存不足时换出 running 中低优先级请求
- **prefix caching**：检测共享前缀，复用 KV Cache
- **监控**：QPS / latency / GPU 利用率 / KV 命中率

## 三面（主管面）

### 10. 对比 DDP 和 ZeRO-3 的通信量
- DDP：每步 all-reduce 梯度，通信量 = 2ψ × (N-1)/N
- ZeRO-3：前向 all-gather 参数 + 反向 all-gather 参数 + reduce_scatter 梯度
- ZeRO-3 通信量 ≈ 3× DDP，但显存从 O(ψ) 降到 O(ψ/N)
- 结论：ZeRO-3 用 1.5× 通信换 N× 显存
- **追问：什么时候选 DDP，什么时候选 ZeRO-3？**
  - 模型放得下：DDP（通信少，吞吐高）
  - 模型放不下：ZeRO-3（牺牲通信换显存）
  - 超大模型：ZeRO-3 + activation checkpointing + CPU offload

### 11. 京东的 AI Infra 场景有什么特点？
- 电商推荐：大量 embedding 表，参数服务器架构
- 搜索 NLP：BERT/大模型推理，低延迟要求

- 物流优化：组合优化 + ML，训练推理混合负载
- 关注成本优化：自研推理框架，量化/蒸馏降部署成本
